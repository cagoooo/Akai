# 評論與評分資料保護規格

紀錄日期：2026-10-12。狀態：第二階段原始碼與隔離測試已新增，尚待本輪 CI、分階段部署與正式驗收；不能視為已完成第二階段上線。

## 目的與範圍

這次把「誰能改評論」與「誰負責計票」分清楚：使用者只能修改自己的心得、評分或點讚，公開統計由後端重新計算。就像學生能交自己的選票，總票數交給老師核算，不能讓每個學生都直接改班級計票表。

本次只調整 `toolReviews`、`toolRatings` 與相應前端／後端契約。沿用既有 Google 與匿名登入，不變更其他集合的資料規格或認證方式；`achievements`、`userAchievements`、`reviewReplies` 保留原邊界，未猜測其用途後新增權限。

主線透過官方 Firebase CLI 的既有認證唯讀取得正式 Firestore 規則，確認與基準提交 `3c1645f6` 相符，並保存備份與 SHA-256。先前直接查詢 API 的 403 已透過正確的既有 CLI 認證流程解決，沒有變更 IAM 或啟用 API。此證據確認的是修改前正式基準，不能替代第二階段新規則部署後的比對。

## 寫入契約

| 項目 | 新規格 |
| --- | --- |
| 評論作者 | 建立時 `userId` 必須等於當前認證 UID；匿名、一般 Google 與管理員身分均遵守同一條件 |
| 工具代碼 | `toolId` 為 1–100000 的整數；這是格式與範圍檢查，未宣稱能證明工具存在於目錄 |
| 評分 | `rating` 為 1–5 的整數 |
| 心得 | `comment` 為字串，最多 500 字元且去除首尾空白後非空；新增與編輯介面／服務一同對齊 |
| 姓名／標題／相片 | `userName` 為 1–80 字元；`toolTitle` 可省略，有值時為 1–200 字元字串；`userPhoto` 可省略、為 `null` 或最多 500 字元字串 |
| 建立欄位 | 嚴格欄位白名單；初始 `likes = 0`、`likedBy = []`，`createdAt` 必須為本次伺服器時間 |
| 作者編輯 | 只能改 `comment`、`rating`、`updatedAt`、`edited`；編輯時間為本次伺服器時間、`edited = true`，作者／工具／建立時間不可變更 |
| 刪除 | 只有原作者可刪除；管理員 client 沒有額外冒名修改或刪除旁路 |
| 本人點讚 | 只允許當前 UID 加入一次或移除一次，其他 UID 保留，計數相應加減 1，不為負且維持安全整數 |
| 統計 | `toolRatings/tool_{id}` 公開可讀；任何前端認證身分均不可直接新增、修改或刪除。後端 Admin SDK 的既有權限不受 client 規則影響 |

## 舊資料相容與不做的遷移

舊評論缺少 `updatedAt`／`edited` 時，作者合法編輯可以新增這兩欄，不必事先批次補寫。

點讚契約在舊文件缺少 `likes` 時使用 0、缺少 `likedBy` 時使用空名單。只有當次合法本人點讚操作才建立缺欄，前端與規則使用同一預設；不是全站批次遷移。原欄位為 `null`、錯誤型別或含重複 UID 時，操作拒絕且不覆寫原資料。

既有票數與名單長度不相同時，保留這個偏差，只對本次合法操作加減一票，不以名單長度強制重建票數。若本人仍在名單但票數為 0，取消點讚會產生負數，因此拒絕，交由後續人工或另行授權的遷移處理。

既有 `toolRatings` 不全站自動重建。相關工具的下一次有效評論新增、評分變更或刪除事件，才重新計算該工具；單純修改心得或點讚不重算、不順便修復其他歷史統計。因此上線後可能暫時仍看到未觸發事件的舊統計，不能宣稱全站舊錯分已修復。

## 後端計票與成本邊界

後端 `akai_syncToolRating` 監聽 `toolReviews/{reviewId}` 的寫入事件，部署區域為 `asia-east1`，允許事件重試。事件快照只決定哪些工具需要重算；分數由交易查詢當下該工具的實際評論後重新計算，並先讀共用統計文件作為交易協調點，避免用舊事件加減票造成重送或亂序重複計分。

新增、改評分與刪除均涵蓋，刪除最後一筆有效評分後歸零；工具代碼若由可信後端變更，重新計算前後兩個工具。非整數或超出 1–5 的舊評分不計分。平均分保留一位小數，星等統計 map 整體替換，其他原有統計欄位保留；結果相同時不重寫。

資源設定為 `maxInstances: 3`、`concurrency: 1`、`timeoutSeconds: 60`。這限制函式同時執行量與單次時間，不等於使用者層級限流，也不保證每次查詢成本固定。每次仍讀取該工具的全部評論，成本隨評論數增加；不能以截斷查詢來降低成本，否則會漏分。

同 UID 重複建立評論、多人或跨 UID 灌票**未完全解決**。目前「已評論過」主要由前端查詢與介面提示控制，規則沒有建立每人每工具唯一性的資料約束；匿名 UID 也不等同已驗證的唯一真人。資源上限能減少瞬間執行量，仍可能排隊或重試，後續需另設提交限流與唯一性政策，不能因已有交易與型別驗證便宣稱完全防灌票。

## 分階段發布與回復

1. 固定本輪提交，確認 Functions 編譯、前端檢查與隔離規則／聚合測試通過；保留舊正式規則與發布版本備份。
2. 先部署 `akai_syncToolRating`，核對函式名稱、區域、事件來源、重試與資源設定。這一層只證明部署設定存在，不代表已完成真實事件驗證。
3. 發布對齊新契約的前端，確認正式資產已更新、評論不再直接改統計、合法編輯與點讚契約相同。此時仍可能有舊頁面執行舊邏輯，部署後需明確標記過渡期。
4. 部署新 Firestore 規則，再次唯讀比對正式內容與本輪提交，確認前端不能直接改統計。必要時依已保存的相容版本回復；不得回復到前端寫統計卻仍被新規則拒絕的組合。
5. 依通知邊界完成正式驗收。若無可隔離通知的測試環境，真實評論提交驗證保留未驗證，不直接向正式通知群組送測試資料。

回復要將後端、前端與規則視為同一份契約，不能只回復其中一層。歷史資料校正或全站重建需要另列範圍、備份、回復方式與授權，本次不執行批次遷移。

## 測試證據與正式驗收不同

- `tests/tool-review.rules.test.ts`：用隔離 Firestore 模擬器及 SDK 驗證合法評論、作者編輯／刪除、本人點讚、缺欄相容與非法操作拒絕。未認證、匿名、Google、管理員身分分別測試。
- `tests/tool-rating-aggregation.emulator.test.ts`：直接呼叫聚合函式，以隔離模擬器的 Admin SDK 交易驗證並行、重送、亂序、改分、刪除、無效資料及不相關事件。這不包含真實 `onDocumentWritten` 的事件派送。
- CI 的規則測試可證明該提交在隔離環境通過；正式規則比對可證明上線的是指定內容；真實觸發器驗證才可證明雲端事件確實派送並產生預期統計。三者不可互相替代。

本輪不使用正式個資或既有評論做攻擊重現，不執行全站重建、不跑會通知正式群組的評論測試。正式登入後資料操作與真實觸發結果若未安排隔離驗證，須保留為未驗證。
